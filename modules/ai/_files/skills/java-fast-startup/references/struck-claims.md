Applies to: claims about CRaC, Leyden AOT caches, CDS and their tooling that circulate in blogs, older notes and earlier reports

# Struck and Contested Claims

TL;DR: The claims below were once believed and then refuted, narrowed or left unresolved by a later
measurement or a primary source. Do not repeat a claim from the left column. Use the corrected wording,
and follow the link to the topic file for the evidence and the context.

How to read the tables:

- **Verdict:** *struck* = refuted by a measurement or a primary source. *Nuanced* = true only under the
  stated conditions. *Contested* = sources disagree, and no measurement here settles it. *Unverified* =
  no source could be checked. *Dropped* = the claim contradicts measured facts and is not repeated.
- **Evidence:** "measured <date>, <JDK>, <setup>" for a measurement, "reported (<kind of source>)" for a
  public source, "not measured" when neither exists. "2026-09" and "2026-08" lines come from earlier
  unpublished measurements by the skill's author ([measuring.md §10](measuring.md#10-team-measurements-and-third-party-numbers));
  their exact JDK build was not recorded (**open inconsistency:** [crac-engines.md](crac-engines.md) Table A and [cds-appcds.md](cds-appcds.md) §7 give Zulu 25.0.4.1 for runs of this kind). "2026-11-15" lines ran in arm64 containers with Zulu 25.0.5
  CRaC; the setup is at the start of [java-debug crac.md](../../java-debug/references/crac.md).
  *Outdated* = was true for an older release only. Combined verdicts such as "struck, limited" add the
  limit of the refutation. "Linux arm64 (OrbStack VM)" and "fresh Mac" are the evidence classes of
  [measuring.md §11](measuring.md#11-linux-vm-measurements) and [§9](measuring.md#9-reference-setup-of-the-fresh-measurement). When a later measurement changes a
  verdict, the row says "Until <date> the verdict was ...", so the old wording stays traceable.
- Origin of this list: the claims were collected from earlier unpublished reports and notes (the author's private notes, not available to the reader) and checked against new
  measurements in 2026-11. Reason it exists: a refuted claim tends to come back from an old source. Limit:
  a verdict holds for the stated JDK, engine and setup only; a newer build can change it.

| CRIU does not run on arm64 with the JVM | struck | The cause is privileges, not the architecture: without `CAP_SYS_PTRACE` CRIU fails with `kcmp ... | ZGC is incompatible with CRaC | struck for `warp` on Zulu 25 and 27 | Refuted for `warp` on Zulu 25 and 27: checkpoint and restore with ZGC worked on the demo app and PetClinic (arm64), and the first request after each restore returned 200. Not tested: CRIU (criuengine) with ZGC on a real app, other JDK vendors, x86 with a real app, load after the restore, ZGC with a database over the network. The OTel agent 2.33.1 blocks the checkpoint with `CheckpointOpenSocketException` (its exporter connection) once it has exported; a checkpoint before any export, or after 330 s idle (one tested idle time after 30 requests; [debug-agents.md §2.4](debug-agents.md#24-opentelemetry-java-agent)), works, and the collector log showed spans after the restore (n = 1 per variant, demo app, collector over a Docker network). Until 2026-11-16 the OTel part was "reported only: no CRaC support" | measured 2026-11-15, Zulu 25.0.5 (JFR); measured 2026-11-16, Linux arm64 (OrbStack VM), Zulu 25.0.5, warp (OTel) | [debug-agents.md](debug-agents.md#24-opentelemetry-java-agent) |
| Leyden forbids agents | nuanced | JEP 483 forbids agents that rewrite classes through `ClassFileLoadHook`. The OTel agent 2.33.1 gets no cache: training fails with SIGSEGV on Temurin 25.0.5 and with `Critical class java.lang.Class has been excluded` on 27.0.1.0.2; `--add-modules=java.instrument` does not help; a cache trained without the agent is rejected (`jdk.module.addmods` mismatch). Until 2026-11-16 the verdict was "contested: reported both to work and to fail". Other agents: check with strict mode | measured 2026-11-16, Linux arm64 (OrbStack VM); reported ([JEP 483](https://openjdk.org/jeps/483); issue-tracker URLs not recorded) for the earlier reports | [leyden-aot.md](leyden-aot.md#9-debuggers-jfr-and-java-agents) |

| An AOT cache works with any collector from JDK 26 | nuanced | The JVM starts, but a cache trained with G1 gave no gain under ZGC on JDK 25, 26 and 27; (19 % slower on 27); a ZGC-trained cache gave -12 % to -22 % on 25 and about -48 % to -54 % on 26 and 27 (two series, [leyden-aot.md §10](leyden-aot.md#10-garbage-collectors)), and under G1 it was 25 % slower on 25 (n = 3) and within noise on 26 and 27. On 27, strict mode also rejects a G1 cache under Parallel or Serial (`AOT Code Cache disabled`). Train with the production collector | measured 2026-11-16, Linux arm64 (OrbStack VM), Temurin 25.0.5, 26.0.2.1, 27.0.1.0.2; reported ([JEP 516](https://openjdk.org/jeps/516)) for the JEP statement | [leyden-aot.md](leyden-aot.md#10-garbage-collectors) |

| JFR works fine with an AOT cache | struck | The cache is discarded unless training and run both use JFR (`jdk.module.addmods` mismatch). JDWP also discards it: "AOT cache has aot-linked classes. | A Leyden cache is architecture-neutral and holds no heap data | struck | A cache is bound to the JDK build, OS, CPU architecture, and the class path (mtime and size of each jar). | An AOT cache is bound to its path | contested | A copy of the jar directory at another path, with the same mtime and size, still used the cache. Absolute paths are embedded in the file. | warp up to 2.9.0 crashes with SIGSEGV on glibc 2.42 | reported, not re-measured | Reported by an earlier unpublished measurement in 2026-09. warp 2.12.0 works on glibc 2.42; the bundled CRIU 3.17.1-crac fails. The single source of this topic is [crac.md §5](../../java-debug/references/crac.md#5-version-traps-and-checkpoint-images) | measured 2026-11-15, Zulu 25.0.5 CRaC, Ubuntu 25.10 | [crac-engines.md](crac-engines.md) |
| Spring 5.3 WAR apps with EclipseLink are unsuitable for CRaC | struck as a general rule | An unpublished Spring 5.3 + EclipseLink 2.7 batch application (a plain jar) checkpoints: cold start 3.4 s, restore 0.8 s. The WAR and servlet-container case was not measured | measured 2026-08, Zulu 25 | [frameworks.md](frameworks.md) |
| A large heap is a problem for warp | struck | A JVM with a 1.2 GB heap restored in 176 ms | measured 2026, exact date not recorded, Zulu 25, warp, Kubernetes on arm64 (earlier run by the skill's author; cluster details not recorded) | [gc-cpu-ram-throughput.md](gc-cpu-ram-throughput.md) |
| A restore is always fast | nuanced | The start time gains by the work the checkpoint skips. A trivial app has almost none to skip: 16-23 ms restore against 18-44 ms cold. A missing warm-up does not make the start slow: PetClinic, checkpointed right after ready without any request, restored in 43-62 ms against 3.0-3.3 s cold. What a missing warm-up costs is the first seconds of throughput: 1048-1220 requests per second in the first 5 s window, like a cold JIT start (1440-1477), against 3020 after a checkpoint taken after a warm-up. A cold page cache adds 0.4-0.5 s (**open inconsistency:** the restore table in [crac-engines.md §4](crac-engines.md#4-engine-speed-and-image-size) differs by only 0.29 to 0.34 s between a warm and a dropped page cache) | measured 2026-11-15, Zulu 25.0.5 CRaC (trivial app); measured 2026-09, x86, Zulu 25 (page cache); measured 2026-11-16, Linux arm64 (OrbStack VM) (PetClinic) | [measuring.md](measuring.md), [gc-cpu-ram-throughput.md §7](gc-cpu-ram-throughput.md#7-throughput-and-warm-up) |
| `-XX:AOTMode=on` and `required` are interchangeable | nuanced | `on` on JDK 24 to 26; `required` from JDK 27, and JDK 25 and 26 reject `required`. Recipes show both | measured 2026-11-16, Temurin 25.0.5 (fresh Mac); measured 2026-11-16, Linux arm64 (OrbStack VM), Temurin 25, 26, 27 | [leyden-aot.md](leyden-aot.md) |
| The Leyden CPU-feature SIGILL is fixed in a known version | unverified | The bug: a cache trained on a CPU with newer instructions (for example AVX-512) crashed with SIGILL on an older CPU. Sources conflict between 25.0.5 and 27 for the fix; the bug ID was not recorded, and the bug tracker could not be read. The mechanism is measured: 328 adapters (call stubs between interpreted and compiled code) from the cache loaded in 56 of 56 runs, even with `UseAVX=0`. Mitigation: `-XX:+UnlockDiagnosticVMOptions -XX:-AOTAdapterCaching`, or train on the weakest CPU | measured 2026-09, x86, JDK 25.0.4 | [leyden-aot.md §11](leyden-aot.md#11-cpu-features-the-sigill-trap) |
| warp support began with the October 2026 release (a statement in Azul's CRaC runtime docs; source URL not recorded) | dropped | Earlier unpublished measurements used warp in 2026-08. Do not repeat the date | measured 2026-08, Zulu 25, warp | [crac-engines.md](crac-engines.md) |
